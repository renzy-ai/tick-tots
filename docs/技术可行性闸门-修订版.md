## 三、关键技术风险评估（修正版）

### 风险 1：数据模型转换（倒计时 → 挂钟）

**描述**：Tot Clock 是"顺序倒计时"模型（第 1 个活动走 30 分钟→第 2 个走 20 分钟），我们需要"挂钟模型"（7:30 在这格、8:00 在那格）  
**复杂度**：高  
**解决方案**：  
- 保留 Tot Clock 的 `activities.ts`（活动定义）和 `timer.ts`（时间计算基础）  
- 新增 `timeline.ts`（挂钟模型）：定义 `startTime`（起床时间）、`endTime`（睡觉时间）、节点绝对时间  
- 时间轴视图组件基于 `timeline.ts` 渲染，不依赖 Tot Clock 的圆钟组件  
**验证方法**：单元测试覆盖跨夜场景  
**风险等级**：🟡 中（逻辑复杂但可控）

---

### 风险 2：跨夜时间轴计算

**描述**：睡觉时间跨夜（20:30 → 07:00），需要处理时间 wrap-around  
**复杂度**：中  
**解决方案**：  
- 使用"起床时间"作为一天起点，时间轴从 0 开始计算相对偏移  
- 跨夜节点特殊标记，不直接比较时间字符串  
**验证方法**：单元测试覆盖跨夜场景  
**风险等级**：🟡 中（逻辑复杂但可解决）

---

### 风险 3：拖拽交互的时间吸附

**描述**：拖拽节点时自动吸附到整点/半点，需要实时计算目标时间  
**复杂度**：中  
**解决方案**：  
- **复用 Tot Clock 的拖拽逻辑**（`ParentPanel.svelte` 的 `setPointerCapture`）  
- 新增吸附算法：±5分钟内吸附到整点/半点，微调模式 1 分钟步长  
- 拖拽过程中显示半透明预览 + 临时时间标签  
**验证方法**：手动测试 + 边界场景（节点重叠）  
**风险等级**：🟢 低（Tot Clock 已验证拖拽稳定性）

---

### 风险 4：多设备同步的配置冲突

**描述**：手机和平板同时修改配置时，可能产生冲突  
**复杂度**：低  
**解决方案**：  
- Last Write Wins 策略（最后修改覆盖）  
- 配置增加 `updatedAt` 时间戳  
- 接收端显示"配置已更新"提示  
**验证方法**：手动测试并发修改  
**风险等级**：🟢 低（单用户场景，冲突概率低）

---

### 风险 5：长时间运行的稳定性

**描述**：挂墙平板 24h 运行，可能出现内存泄漏或定时器漂移  
**复杂度**：中  
**解决方案**：  
- **复用 Tot Clock 的时间漂移补偿**（每次 tick 计算实际流逝时间）  
- 定期清理已过去的节点（避免 DOM 过长）  
- Wake Lock 失败时降级为普通模式  
**验证方法**：连续运行 72h 测试  
**风险等级**：🟢 低（Tot Clock 已验证长时间运行）

---

### 风险 6：Bun → Node 改写

**描述**：Tot Clock 的 `server.ts` 使用 `Bun.serve`，Node.js 无法直接运行  
**复杂度**：低  
**解决方案**：  
- 用 Node 原生 `http` 模块改写（约 85 行代码）  
- 保持 API 接口不变（`/api/state`、`/api/settings`）  
- 保持 SSE 推送逻辑不变  
**验证方法**：手动测试 API 响应  
**风险等级**：🟢 低（简单改写，无复杂逻辑）

## 五、技术约束与限制

### 必须遵守的约束

1. **底座对齐**：技术栈必须与 Tot Clock 一致（Svelte 5 + Vite + TypeScript）
2. **复用优先**：能复用 Tot Clock 的模块就复用，不重复造轮子
3. **浏览器兼容**：Chrome 90+ / Edge 90+ / Android WebView（**明确不支持 iOS**）
4. **零第三方依赖**：后端只用 Node.js 内置模块（http/fs/events）
5. **隐私保护**：数据不出局域网，不上传云端

### 已知的平台限制（移除 iOS）

1. **后台定时器**：Android Chrome 节流，但挂墙场景页面始终在前台，影响不大
2. **Wake Lock**：Android 支持良好，iOS 不支持（但已明确不做 iOS）
3. **PWA 安装**：Android Chrome 支持自动提示"添加到主屏幕"

## 六、可行性结论

### 总体评估：✅ 可行（基于复用）

**理由**：
1. **底座成熟**：Tot Clock 已验证核心技术（时间漂移补偿、拖拽交互、Wake Lock、防误触）
2. **风险可控**：6 个风险点中 4 个低风险，2 个中风险（数据模型转换、跨夜计算）有明确方案
3. **复用价值高**：约 40% 代码可直接复用，节省开发工时
4. **架构简单**：零依赖 + 局域网部署，维护成本低

### 关键成功因素

1. **复用策略**：明确哪些模块复用、哪些新建，避免"改着改着变成重写"
2. **数据模型**：挂钟模型是核心，必须先写单元测试确保跨夜/吸附逻辑正确
3. **Bun→Node 改写**：简单但繁琐，需保持 API 接口一致
4. **时间轴视图**：Tot Clock 没有线性时间轴，需要从零设计，是最大的工作量

### 建议的技术实施顺序

1. **第一阶段（底座）**：克隆 Tot Clock → 移除圆钟相关代码 → 适配中文 → Bun→Node 改写
2. **第二阶段（模型）**：新建 `timeline.ts`（挂钟模型）+ 单元测试
3. **第三阶段（视图）**：新建时间轴组件（直条 + 睡觉弧 + 游标 + 三态）
4. **第四阶段（交互）**：复用 ParentPanel + 新增时间吸附算法
5. **第五阶段（提醒）**：Web Audio 蜂鸣 + 提醒调度
6. **第六阶段（收尾）**：PWA 配置 + 多设备测试 + 稳定性测试
